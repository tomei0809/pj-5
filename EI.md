## 1. プロジェクトの進め方・データ形式の詳細

### 1.1 概要

動画を読み込み、**1秒ごとの「見どころ度」を予測**して、見どころ区間を切り抜く「動画自動編集AI」を作る。5人チーム。

```
動画 (videos/*.mp4)
  │  features/extract_features.py   動画 → 1秒ごとの特徴量
  ▼
data/features/{visual,audio,text}/{video_id}.npy   形（秒数, 次元）
  │  train.py + systems/{system}.py  特徴量 + 正解 → モデルを学習
  ▼
runs/{system}_{modality}_seed{n}/   best.pt, pred_val.csv, summary.json
  │  評価スクリプト・統合（評価・統合担当）
  ▼
統合スコア（video_id, t, score）
  │  highlight/predict.py → highlight/clip.py
  ▼
切り抜き区間 CSV / クリップ (outputs/*.mp4)
  │  frontend/   グラフ・見どころランキング・区間再生
```

※ MoSu は特徴量が配布されているので、MoSu で学習・評価する間は `features/extract_features.py` は使わない。代わりに `tools/prepare_mosu.py` で MoSu を `train.py` の形（`data_mosu/` など）に変換する。新しい動画（TVSum・自分たちの動画）を使うときに `features/` が必要になる。
※ 学習済みの重みで予測と正解を重ねて見るプロトタイプは `tools/demo_mosu.py`（`demo_out/` に出力）。

### 1.2 担当とやること

| 担当           | 人数 | やること                                                                                                                                                                                                                            |
| -------------- | ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 学習システム   | 3人  | ①各自で学習システムを実装（`systems/{自分のシステム名}.py`）<br>②映像・音声・字幕の3つすべてを、シード0・1・2で学習し、valの予測CSV（`pred_val.csv`）を提出<br>③比較の後、各自が担当する情報（モダリティ）を1つ決めて改良           |
| 評価・統合     | 1人  | ①正解ラベル（Most Replayed を1秒単位にしたもの）の変換コード。動作確認用に数十本分を先に渡し、変換方法とジャンルが決まったらまとめて変換<br>②評価方法の検討、評価スクリプト、「システム×情報」の比較表<br>③単純平均と重み付きの統合 |
| フロントエンド | 1人  | ①ジャンルの下調べ（テーマごとの動画数、test にある日本語動画の数）→全員でジャンル決定<br>②Most Replayed を仮スコアにして、グラフ・見どころランキング・区間再生（YouTube埋め込み）<br>③予測がそろったら統合スコアに差し替え          |

### 1.3 進め方（順番）

1. uv 環境を統一する（Python・PyTorch のバージョン）
2. 評価・統合担当が動作確認用の正解ラベル（数十本）を配る
3. 学習担当は `--subset` で小さく動作確認 → 本番（3モダリティ × 3シード）
4. `pred_val.csv` を提出 → 評価・統合担当が比較表を作る
5. 比較を見て、各自が改良するモダリティを決める
6. 統合 → フロントエンドを統合スコアに差し替え
7. **test は最後に一度だけ** 使う

### 1.4 統一すること

| 項目       | 内容                                                                                                                                                                                                                           |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 分割       | MoSu 公式のものを使う（ジャンルごとに train 8 : val 1 : test 1）                                                                                                                                                               |
| 正解ラベル | 評価・統合担当が作ったものを全員で使う（各自で作らない）                                                                                                                                                                       |
| 学習率     | 全員同じ固定値（`train.py` の既定 `--lr 1e-3`。値は確定待ち → 5章）                                                                                                                                                            |
| エポック   | 最大50。valの基準が5回続けて改善しなければ終了し、一番良かった時点のモデルを使う<br>（README の「(？)」の部分は `train.py` に実装済み：`--max_epochs 50` `--patience 5`、最良時点を `best.pt` に保存し、最後に読み戻して予測） |
| シード     | 0・1・2 の3回（`jobs/train.sbatch` が順に実行）                                                                                                                                                                                |
| 環境       | uv の環境を統一（`.python-version` = 3.12、`pyproject.toml` = `torch>=2.13.0`（CUDA 13.2 版）、`numpy`、`h5py`、`fsspec[http]`、`matplotlib`）。`uv.lock` はコミット済み → 全員 `uv sync --locked`                          |
| 評価       | 方法は全員共通（検討中）。判断はすべて val、test は最後に一度だけ                                                                                                                                                              |
| 記録       | 学習時間・パラメータ数・使ったGPU は `train.py` が `summary.json` に自動で記録                                                                                                                                                 |

### 1.5 使用データ

| データ             | 用途                   | 内容                                                                                                                                                                                                                      |
| ------------------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **MoSu**（中心）   | 学習・主な評価         | 約5万3千本の YouTube 動画。映像・字幕・音声の特徴量と、視聴者の「最も再生された部分（Most Replayed）」の統計に基づく見どころ度が配布されている<br>特徴量はすべて768次元（visual=CLIP、audio=AST、text=RoBERTa）。ジャンルは `cluster_id`（0〜9）<br>Hugging Face：https://huggingface.co/datasets/hminjeong/TripleSumm-MoSu （CC BY 4.0） |
| TVSum（補助）      | 補助的な評価・追加学習 | 生動画が入手でき、人手による見どころ度つき                                                                                                                                                                                |
| 自作ラベル（補助） | 補助的な評価・追加学習 | メンバー自身が見どころ度を付けた動画                                                                                                                                                                                      |

### 1.6 ファイル形式

- 時間の単位は **1秒**、動画IDは **MoSu のID** を使う

| 種類         | 形式 | 置き場所                                           | 中身                                                            |
| ------------ | ---- | -------------------------------------------------- | --------------------------------------------------------------- |
| 特徴量       | npy  | `data/features/{visual,audio,text}/{video_id}.npy` | 形（秒数, 次元）float32                                         |
| 正解ラベル   | npy  | `data/labels/{video_id}.npy`                       | 形（秒数,）0〜1。今は MoSu の `gt_score` をそのまま使う仮のもの |
| 分割         | txt  | `data/splits/{train,val,test}.txt`                 | 1行に1つの動画ID                                                |
| 予測         | CSV  | `runs/.../pred_val.csv`                            | `video_id,t,score`。score は動画ごとに0〜1へ正規化              |
| 切り抜き区間 | CSV  | （未定）                                           | `video_id,rank,start,end`                                       |
| 学習記録     | JSON | `runs/.../summary.json`                            | best_epoch, best_val_error, train_sec, n_params, gpu, args, log |

- 特徴量と正解の秒数がずれているときは、`train.py` が短い方に合わせる
- 予測CSVの例：

```csv
video_id,t,score
abc123,0,0.120000
abc123,1,0.850000
```

## 3. 学習システムの候補と比較

難易度・おすすめ度は ★1〜5（★が多いほど難しい / おすすめ）。すべて `build_model` と `train_one_epoch` の形に収まる。

| 手法                       | 内容                               | 難易度 | おすすめ度 | 長所                                           | 短所                                            | 実装メモ                                                                     |
| -------------------------- | ---------------------------------- | ------ | ---------- | ---------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------- |
| 1次元CNN                   | 時間方向の畳み込み                 | ★☆☆☆☆  | 済         | 速い・安定                                     | 近くの秒しか見えない                            | 実装済み                                                                     |
| GRU                        | 再帰で時間順に処理                 | ★★☆☆☆  | 済         | 前後の流れを使える                             | 長い動画で遅い                                  | 実装済み                                                                     |
| MLP（ベースライン）        | 各秒を独立に全結合                 | ★☆☆☆☆  | ★★★☆☆      | 比較の基準になる                               | 時間の流れを使わない                            | `nn.Sequential` だけで済む                                                   |
| 双方向LSTM / GRU           | 前後両方向の再帰                   | ★★☆☆☆  | ★★★☆☆      | 未来の文脈も使える                             | GRU と結果が近くなりやすい                      | `bidirectional=True`。詰め物の影響を避けるため `pack_padded_sequence` を使う |
| **TCN**（拡張畳み込み）    | dilation を倍々にした1次元CNN      | ★★☆☆☆  | ★★★★☆      | CNN の速さで広い範囲を見られる                 | 層の設計が必要                                  | `nn.Conv1d(..., dilation=2**i, padding=...)` を積む。出力に `M` を掛ける     |
| **Transformer Encoder**    | 自己注意で動画全体を見る           | ★★★☆☆  | 済         | 遠く離れた秒の関係も使える。見どころ推定の定番 | 長い動画でメモリ大（秒数の2乗）                 | `systems/transformer.py` で実装済み（3.2 参照）                              |
| CNN + Transformer          | CNN で局所特徴 → Transformer       | ★★★☆☆  | ★★★★☆      | 局所と全体の両方                               | パラメータが増える                              | 既存の CNN を前段に流用できる                                                |
| ローカル注意（PGL-SUM 風） | 区間ごとの注意 + 全体の注意        | ★★★★☆  | ★★★☆☆      | 長い動画に強い                                 | 実装がやや複雑                                  | 区間分割とマスクの扱いに注意                                                 |
| 1次元 U-Net                | 縮小→拡大の畳み込み + スキップ接続 | ★★★☆☆  | ★★★☆☆      | 粗い流れと細かい変化の両方                     | 秒数が割り切れないときの処理                    | 末尾を詰めてから戻す                                                         |
| Mamba / S4 系              | 状態空間モデル                     | ★★★★★  | ★★☆☆☆      | 長い系列を線形時間で                           | 追加ライブラリ・CUDA 依存、環境統一が崩れやすい | 入れるなら全員に相談（`pyproject.toml` が変わる）                            |

**おすすめの順番**：Transformer Encoder → TCN → 双方向LSTM（CNN・GRU との比較がしやすい）

### 3.1 1次元CNN・GRU・Transformer Encoder の比較

実装済みの3つを、手法としての一般的な性質で比べたもの。CNN・GRU の細かい設定（層数・幅など）は、push したあとで各自が追記する。

| 観点                   | 1次元CNN                                | GRU                                            | Transformer Encoder                                              |
| ---------------------- | --------------------------------------- | ---------------------------------------------- | ---------------------------------------------------------------- |
| 見える範囲             | カーネル幅 × 層数の近くの秒だけ         | 前から順に積み上げた流れ（単方向なら過去だけ） | 動画全体のすべての秒を一度に見る                                 |
| 計算量・メモリ         | 秒数に比例（軽い）                      | 秒数に比例                                     | **秒数の2乗**（長い動画で重い）                                  |
| 並列化・速度           | 時間方向も並列で速い                    | 1秒ずつ順番に処理するので遅い                  | 並列で速い（ただし長い動画ではメモリが先に足りなくなる）         |
| 長い動画               | 遠くの秒は見えない                      | 遠くの情報が薄れやすい                         | 遠くの秒も直接見られるが、メモリが課題                           |
| 位置（順番）の情報     | 畳み込みが自然に持つ                    | 処理の順番が自然に持つ                         | 持たないので**位置エンコーディングが必要**                       |
| 詰め物 `M` の扱い      | 出力に `M` を掛ける。端で詰め物が混ざる | `pack_padded_sequence` か、最後に `M` で除く   | `src_key_padding_mask=~M` で注意の対象から外せる（混ざらない）   |
| lr=1e-3 固定での安定性 | 安定                                    | おおむね安定（勾配クリッピングがあると安心）   | やや不安定になりやすい → Pre-LN と勾配クリッピングで対策         |
| パラメータ数の目安     | 少ない                                  | 中くらい                                       | 中くらい（`transformer.py` の設定で約36万、入力768次元の場合）   |
| 得意な見どころの形     | 短く急な変化（盛り上がりの瞬間）        | 前後の流れでだんだん高まる場面                 | 動画全体の中で「どこが一番か」の相対的な判断                     |
| 比べるときに見るところ | 速さ・安定性の基準                      | CNN との差＝流れを使う効果                     | CNN・GRU との差＝全体を見る効果。学習時間と GPU メモリも記録する |

### 3.2 systems/transformer.py の設定

| 項目                                           | 値                                                      | 理由                                                                                     |
| ---------------------------------------------- | ------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 入力の射影                                     | `nn.Linear(in_dim, 128)`                                | 特徴量の次元をモデルの幅にそろえる                                                       |
| 位置エンコーディング                           | sin/cos（秒数に合わせて毎回作る）                       | 動画の長さがバラバラでも最大長を決めなくてよい                                           |
| `d_model` / `nhead` / 層数 / `dim_feedforward` | 128 / 4 / 2 / 256                                       | 小さめにして、長い動画でもメモリに収まりやすくする                                       |
| dropout                                        | 0.1                                                     | 一般的な値                                                                               |
| `norm_first=True`（Pre-LN）                    | —                                                       | lr=1e-3 固定でも学習が安定しやすい。最後に `LayerNorm` を1つ足す                         |
| マスク                                         | `src_key_padding_mask=~M`                               | `M` は有効な秒が True なので反転して渡す。詰め物ありとなしで出力が一致することを確認済み |
| 出力                                           | ロジット（`nn.Linear(128, 1)`）                         | 評価前に動画ごとに0〜1へ正規化されるので、sigmoid は掛けない                             |
| 損失                                           | `binary_cross_entropy_with_logits` を有効な秒だけで平均 | 正解が0〜1なので BCE が使える                                                            |
| 勾配クリッピング                               | `clip_grad_norm_(..., 1.0)`                             | 学習率を変えずに、学習が暴れるのを防ぐ                                                   |

- 値はファイルの先頭の定数（`D_MODEL` `N_HEAD` `N_LAYERS` `D_FF` `DROPOUT` `CLIP`）で変えられる
- **GPU メモリが足りないとき**：まず `--batch_size` を下げる → それでも足りなければ `N_LAYERS` や `D_MODEL` を下げる（`N_HEAD` は `D_MODEL` を割り切れる数にする）

**損失の工夫**（`train_one_epoch` の中だけで変えられる）

| 損失           | 内容                                  | メモ                                                       |
| -------------- | ------------------------------------- | ---------------------------------------------------------- |
| MSE            | 正解との二乗誤差                      | 基本。今の `val_error` と同じ考え方                        |
| ランキング損失 | 「正解が高い秒 > 低い秒」の順序を学ぶ | 見どころの順位を重視する評価（Kendall τ など）に合いやすい |
| 相関損失       | 1 − ピアソン相関                      | 動画ごとの大きさの違いに影響されない                       |

※ 比較の公平さのため、lr・最大エポック・patience・シードは変えない。変えてよいのはモデルの形と損失。

### 4.2 大規模データの扱い（容量・通信）

| 項目                      | 何が起きるか                                                                                                                                            | 対策                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |

### 4.3 コードの共有・ブランチ・整合性

**ブランチの使い方**

```
main                      いつでも動く状態。直接 push しない
└── feature/<名前>-<内容>  各自の作業（例：feature/ei-transformer）
```

1. 作業前に `git switch main` → `git pull`
2. `git switch -c feature/<名前>-<内容>` でブランチを作る
3. こまめにコミット → `git push -u origin feature/<名前>-<内容>`
4. GitHub で Pull Request（PR）を作り、**1人以上に見てもらってから** main に入れる
5. 長く作業するときは、ときどき `git pull origin main`（または rebase）で main の変更を取り込む

**ルール**

- 自分の `systems/{名前}.py` 以外は書き換えない
- 共通部分（`train.py`、`pyproject.toml`、`uv.lock`、`jobs/`、`val_error`、データ形式）を変えるときは**先にチームに相談**し、PR にまとめて変更する
- `uv.lock` ができたらコミットして、全員 `uv sync --locked` で同じ環境にする。パッケージを追加したいときは相談
- 提出する結果は「どのコミットで学習したか」がわかるようにする（PR 番号やコミットIDを9章に書く）
- データ・学習済みモデル・動画はコミットしない（共有は共有領域で）
- コミットメッセージは「何をしたか」を日本語で短く（例：`systems/transformer.py を追加`）
- 変更したら **9章の記録履歴に1行書く**

## 6. 用語集

| 用語                   | 意味                                                                                                  |

| 見どころ度（スコア）   | 各秒がどれだけ「見どころ」か。0〜1                                                                    |

## 8. 今やること：transformer を学習させる手順

`systems/transformer.py` をサーバの GPU で学習させるまでの流れ。詳しいことは `docs/server_setup.md`。

**3つの場所**（どこで何をするか）

| 場所                     | ここでやること                                                     |
| ------------------------ | ------------------------------------------------------------------ |
| ① 自分のPC               | コードを書く・push する、サーバに ssh する                         |
| ② ログインノード（受付） | `git pull`、`uv sync`、データの準備、`sbatch`（ジョブの申し込み）  |
| ③ 計算ノード（GPU）      | `train.py` が動く（ジョブを出すと自動で動く。自分で入る必要はない） |

- ②で重い処理（学習）はしない。学習は必ず `sbatch` で③にやってもらう
- コマンドはすべて**プロジェクトのフォルダ（`~/<リポジトリ名>`）で**実行する

### 8.1 最初に1回だけ（済んでいればとばす）

1. 学内ネットか VPN につないで、①から `ssh s<学籍番号>@<サーバのアドレス>`
2. 公開鍵の登録、サーバから GitHub への鍵の登録（`docs/server_setup.md` 1-2・1-3）
3. ②で `git clone git@github.com:tkg-tus/pj-5.git` → `cd pj-5`
4. ②で `uv sync --locked`（`.venv` ができる。数分かかる）

### 8.2 transformer.py をサーバに持っていく

**2026-11-04 に main へ push 済み（d76d96e）** → ②で `git pull` するだけでよい。以下は今後ファイルを変えたとき用。


  ②で `git fetch` → `git switch feature/ei-transformer`。main に入れるのは、PR を作って1人以上に見てもらってから

- **push せずに試すだけ**（①で）：`scp systems/transformer.py s<学籍番号>@<サーバのアドレス>:~/pj-5/systems/`
